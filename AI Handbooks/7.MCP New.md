# MCP Handbook for Backend Developers

Beginner to intermediate · Python · Model Context Protocol · Hands-on labs

This handbook explains the Model Context Protocol (MCP), its architecture, popular MCP servers, and how to build two working Python examples: a calculator server and an exchange-rate MCP tool using the Frankfurter API.

## Learning objectives

By the end of this handbook, you will be able to:

* Understand what MCP is and why it was created.

* Explain the responsibilities of an MCP host, client, and server.

* Understand how MCP tools, resources, prompts, and transports work.

* Identify popular MCP servers and their use cases.

* Build and run a basic `calculator_server.py`.

* Build an exchange-rate tool that retrieves the latest available currency rate from Frankfurter without an API key.

* Test an MCP server using an MCP client or inspector.

## 1. What is MCP?

MCP (Model Context Protocol) is an open protocol that standardizes how AI applications connect to external tools, data sources, and services.

Without MCP, developers often create custom integrations for every AI application and external service. MCP provides a common interface so compatible AI applications can discover and use capabilities exposed by MCP servers.

Think of MCP as a standard connector between an AI application and backend capabilities.

For example, suppose you are building an AI assistant that can:

* Perform calculations.

* Retrieve exchange rates.

* Query a PostgreSQL database.

* Read files.

* Search documentation.

* Interact with GitHub.

Instead of writing a separate integration pattern for every AI application, you can expose these capabilities through MCP servers.

### Traditional integration vs. MCP

| Aspect                 | Traditional custom integration                         | MCP-based integration                                            |
| ---------------------- | ------------------------------------------------------ | ---------------------------------------------------------------- |
| Integration approach   | Custom implementation for each application and service | Standardized protocol                                            |
| Tool discovery         | Often implemented manually                             | Servers can expose discoverable tools                            |
| Input/output           | Application-specific contracts                         | Structured tool definitions and results                          |
| Reusability            | Often tied to one application                          | Can be reused by compatible MCP clients                          |
| Backend implementation | API clients, SDKs, custom wrappers                     | MCP server wrapping APIs, SDKs, databases, or other capabilities |

Important: MCP does not replace your REST APIs, databases, or business services. It provides a standard way for AI applications to interact with them.

## 2. Why was MCP created?

AI models are good at understanding natural language and generating responses, but they do not automatically have access to your company's internal systems, live exchange rates, private documents, or operational APIs.

Developers need a controlled mechanism to connect these capabilities to AI applications.

### Example: AI-powered currency assistant

A user asks:

> What is the latest available USD-to-AED exchange rate?

The flow is:

1. The user sends the question to an AI application.

2. The model determines that it needs current exchange-rate data.

3. The application invokes an MCP tool named `get_exchange_rate`.

4. The MCP server calls the Frankfurter API.

5. The server returns the rate and observation date.

6. The model explains the result to the user.

MCP standardizes the interaction between the application and the tool. Frankfurter remains the source of the exchange-rate data.

## 3. Core building blocks of MCP

MCP uses a client-server architecture with three primary participants: Host, Client, and Server. The protocol also defines the capabilities a server can expose, such as tools, resources, and prompts.

### 3.1 Host, Client, and Server

| Component | What it is                                 | Responsibilities                                                                        | What servers provide                                                                          | How communication works                         |
| --------- | ------------------------------------------ | --------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------- | ----------------------------------------------- |
| Host      | The AI application used by the user        | Manages the LLM, user interaction, MCP connections, permissions, and tool orchestration | Makes server capabilities available to the model through the client                           | Coordinates user/model requests and MCP clients |
| Client    | The MCP protocol component inside the host | Connects to a server, discovers capabilities, sends requests, and processes responses   | Receives tool definitions and access to supported resources/prompts through protocol messages | Uses MCP messages over a supported transport    |
| Server    | A program that exposes capabilities        | Implements tools, resources, prompts, and integrations with backend systems             | Functions, data, templates, and access to external systems                                    | Receives MCP requests and returns results       |

A host generally maintains a separate MCP client connection for each server it connects to. The server does not normally communicate directly with the LLM; the host coordinates the interaction.

### 3.3 The three core server capabilities

Tools — perform actions

Executable functions that the AI application can invoke, such as calculating values, calling an API, creating a ticket, or querying a database.

Example: `get_exchange_rate(base, quote)`

Resources — provide context

Data that an MCP client can retrieve and use as context, such as documentation, configuration, file contents, or database records.

Example: `database://schema`

Prompts — provide reusable templates

Predefined prompt templates that help users or applications perform repeatable tasks.

Example: `summarize_api_documentation(topic)`

| Capability | Typical control                                                                       | Example                       |
| ---------- | ------------------------------------------------------------------------------------- | ----------------------------- |
| Tools      | Model/application decides when to invoke, subject to host policies and user approvals | Call a currency API           |
| Resources  | Application/client decides which context to retrieve and use                          | Read a database schema        |
| Prompts    | Often selected by the user or application                                             | Generate a code-review prompt |

The protocol makes these capabilities discoverable. Exposing a tool does not mean it is automatically called; the host and model determine how it fits into a request.

### 3.4 How MCP communication works

MCP defines two important layers:

* Data layer: Uses JSON-RPC message conventions to represent requests, responses, notifications, and capability interactions.

* Transport layer: Carries those messages between the client and server.

Two commonly used transports are:

| Transport       | How it works                                                                                  | Common use case                                                       |
| --------------- | --------------------------------------------------------------------------------------------- | --------------------------------------------------------------------- |
| STDIO           | The host launches a local server process and exchanges messages through standard input/output | Local Python tools, filesystem integrations, development utilities    |
| Streamable HTTP | The client communicates with a server over HTTP, with optional streaming support              | Remote services, shared server deployments, cloud-hosted integrations |

For the following Python labs, we will use STDIO because it is straightforward for local development.

## 5. Setting up your first MCP server — `calculator_server.py`

In this lab, we will create a simple MCP server that exposes two tools: `add` and `multiply`.

### Step 1: Create a project

Make sure Python 3.10 or a compatible version supported by your installed MCP SDK is available. Python 3.11 or later is a sensible starting point for a new project.

Bash

```
mkdir mcp-handbook
cd mcp-handbook

python3 -m venv .venv
source .venv/bin/activate

python -m pip install --upgrade pip
pip install "mcp[cli]"
```

If you use a Mac with zsh, the activation command above is appropriate. On Windows, activate the virtual environment with `.venv\Scripts\activate`.

### Step 2: Create `calculator_server.py`

Python

Run

```
from mcp.server.fastmcp import FastMCP

# Create the MCP server
mcp = FastMCP("Calculator Server")


@mcp.tool()
def add(a: float, b: float) -> float:
    """Add two numbers and return the result."""
    return a + b


@mcp.tool()
def multiply(a: float, b: float) -> float:
    """Multiply two numbers and return the result."""
    return a * b


if __name__ == "__main__":
    mcp.run(transport="stdio")
```

### Step 3: Understand the code

| Code                           | Purpose                                         |
| ------------------------------ | ----------------------------------------------- |
| `FastMCP("Calculator Server")` | Creates the server and identifies it            |
| `@mcp.tool()`                  | Registers the decorated function as an MCP tool |
| `add(a, b)`                    | Implements the addition operation               |
| `multiply(a, b)`               | Implements the multiplication operation         |
| `mcp.run(transport="stdio")`   | Starts the server using standard input/output   |

The SDK uses Python type hints and function descriptions to help construct the tool's input schema and description.

### Step 4: Test with MCP Inspector

MCP servers using STDIO are generally launched by an MCP client. Running the script directly does not create a normal interactive calculator terminal.

One convenient way to test the server is with MCP Inspector.

Open a separate terminal in your project directory, activate the same virtual environment, and run:

Bash

```
mcp dev calculator_server.py
```

If your installed SDK version provides the `mcp dev` command, it launches the development inspector workflow. Follow the displayed instructions to open the inspector and connect to the server.

Alternatively, launch the Inspector separately:

Bash

```
npx -y @modelcontextprotocol/inspector
```

Use the connection options in the Inspector to launch or connect to your server according to the installed Inspector version. See the [official Inspector repository](https://github.com/modelcontextprotocol/inspector) for current instructions.

Expected result:

### What did we build?

We created an MCP server that advertises two tools. An MCP client can discover these tools, inspect their input schemas, and invoke them using the protocol.

Notice that we did not implement the JSON-RPC messaging, connection lifecycle, or tool discovery manually. The Python SDK handles the protocol details.

### 6.1 What are we building?

We will create a tool named `get_exchange_rate` that accepts two inputs:

* `base`: The currency to convert from, such as `USD`.

* `quote`: The currency to convert to, such as `AED`.

The tool calls Frankfurter's single-pair endpoint:

### 6.3 Create `exchange_rate_server.py`

Use the same project and virtual environment from the calculator lab. The `mcp[cli]` package is already installed there.

Create a file named `exchange_rate_server.py` with the following code.

Python

Run

```
import json
import re
from urllib.error import HTTPError, URLError
from urllib.request import Request, urlopen

from mcp.server.fastmcp import FastMCP

mcp = FastMCP("Exchange Rate Server")

API_BASE_URL = "https://api.frankfurter.dev/v2/rate"


@mcp.tool()
def get_exchange_rate(base: str, quote: str) -> str:
    """
    Get the latest available exchange rate between two currencies.

    Args:
        base: Three-letter source currency code, e.g. USD.
        quote: Three-letter target currency code, e.g. AED.

    Returns the exchange rate and observation date.
    """
    base = base.strip().upper()
    quote = quote.strip().upper()

    # Validate the expected currency-code format.
    if not re.fullmatch(r"[A-Z]{3}", base):
        return "Error: base must be a three-letter currency code."

    if not re.fullmatch(r"[A-Z]{3}", quote):
        return "Error: quote must be a three-letter currency code."

    url = f"{API_BASE_URL}/{base}/{quote}"
    request = Request(
        url,
        headers={"User-Agent": "MCP-Exchange-Rate-Demo/1.0"},
    )

    try:
        with urlopen(request, timeout=15) as response:
            data = json.loads(response.read().decode("utf-8"))

        rate = data["rate"]
        date = data["date"]
        actual_base = data["base"]
        actual_quote = data["quote"]

        return (
            f"Exchange rate: 1 {actual_base} = {rate} {actual_quote}\n"
            f"Observation date: {date}"
        )

    except HTTPError as exc:
        if exc.code == 404:
            return (
                f"Error: No rate found for {base}/{quote}. "
                "Check that both currencies are supported."
            )
        return f"Error: Frankfurter returned HTTP {exc.code}."

    except (URLError, TimeoutError):
        return (
            "Error: Could not reach Frankfurter. "
            "Check your network connection and try again."
        )

    except (json.JSONDecodeError, KeyError, TypeError, ValueError):
        return "Error: Received an unexpected response from Frankfurter."


if __name__ == "__main__":
    mcp.run(transport="stdio")
```

### 6.4 Understand the implementation

| Code section                      | Purpose                                                  |
| --------------------------------- | -------------------------------------------------------- |
| `FastMCP("Exchange Rate Server")` | Creates the MCP server                                   |
| `@mcp.tool()`                     | Registers the function as an MCP tool                    |
| `base` and `quote`                | Accept the input currency codes                          |
| `.strip().upper()`                | Normalizes inputs such as `usd` to `USD`                 |
| Regular expression                | Checks that each input has three letters                 |
| `urlopen(request, timeout=15)`    | Calls Frankfurter and limits the request duration        |
| `json.loads(...)`                 | Parses the API response                                  |
| `rate` and `date`                 | Extracts the exchange rate and observation date          |
| `except` blocks                   | Handles HTTP, connectivity, timeout, and response errors |
| `mcp.run(transport="stdio")`      | Starts the MCP server                                    |

Backend developer takeaway: The business logic is an ordinary Python function. The MCP SDK exposes it to compatible clients through a standardized tool interface.

The three-letter validation checks the input format, not whether a currency exists. The Frankfurter API remains responsible for confirming that a supported currency pair is available.

### 6.6 Test error scenarios

A backend service should be tested for invalid inputs and upstream failures, not just successful requests.

| Test case            | Input or condition  | Expected behavior                      |
| -------------------- | ------------------- | -------------------------------------- |
| Valid pair           | `USD`, `AED`        | Returns rate and date                  |
| Lowercase inputs     | `usd`, `aed`        | Normalizes and attempts lookup         |
| Invalid format       | `US`, `AED`         | Returns validation error               |
| Unsupported currency | `XXX`, `AED`        | Reports missing rate or upstream error |
| Network failure      | API unreachable     | Returns connectivity error             |
| Slow response        | API exceeds timeout | Returns timeout-related error          |

Note that unsupported pairs may result in different HTTP errors depending on the API's response. The server should report the failure without inventing an exchange rate.

### 6.7 How does an AI application use this tool?

After you connect the server to an MCP-compatible host, you can ask:

> Convert 100 USD to AED using the latest available exchange rate.

The AI application can:

1. Discover `get_exchange_rate`.

2. Recognize that the request needs exchange-rate data.

3. Invoke the tool with `base="USD"` and `quote="AED"`.

4. Receive the rate and observation date.

5. Multiply the returned rate by 100 and explain the result.

For example, if the API returned a rate of `3.67`, the calculation would be:

100×3.67=367 AED100 \times 3.67 = 367\ \text{AED}100×3.67=367 AED

This is an illustrative calculation, not a live quote.

MCP enables the tool call, but the LLM does not become the source of the exchange rate. The rate comes from Frankfurter, while the model interprets the result and responds to the user.

### 6.8 Connect the server to an MCP host

For a local host that supports STDIO servers, configure it to launch the Python interpreter in your virtual environment and pass the path to `exchange_rate_server.py`.

A typical configuration has this shape:

JSON

```
{
  "mcpServers": {
    "exchange-rate": {
      "command": "/absolute/path/to/mcp-handbook/.venv/bin/python",
      "args": [
        "/absolute/path/to/mcp-handbook/exchange_rate_server.py"
      ]
    }
  }
}
```

Replace both paths with the actual absolute paths on your computer. The configuration format and location vary by host, so follow the documentation for your chosen application.

When using STDIO, do not print debugging messages to standard output because the protocol uses that stream for communication. Use logging to standard error instead.

Both servers use the same fundamental MCP pattern. Once you understand the calculator example, the exchange-rate example shows how to integrate external backend services without changing that pattern.

## 8. Key takeaways

* MCP is a protocol, not an LLM, agent framework, database, or replacement for REST APIs.

* The host coordinates the AI application and manages client connections.

* The client communicates with an MCP server and discovers its capabilities.

* The server exposes tools, resources, and prompts.

* Tools execute functions or actions; resources supply contextual data; prompts provide reusable templates.

* STDIO is convenient for local servers, while Streamable HTTP supports remote server communication.

* The Python SDK's `FastMCP` abstraction simplifies server development.

* An MCP server can wrap a third-party API, as demonstrated by the Frankfurter exchange-rate tool.

* Always validate inputs, handle upstream errors, protect credentials, and apply appropriate authorization to tools that access sensitive systems or modify data.
