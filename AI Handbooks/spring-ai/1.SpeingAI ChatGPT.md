# Part 1 --- Spring AI Fundamentals

## 1. Introduction to Spring AI

### 1.1 What is Spring AI?

Spring AI is a framework that helps Java developers integrate generative
AI into Spring applications. It provides consistent abstractions for
chat models, prompts, embeddings, vector stores, tool calling, advisors,
and MCP.

Without a framework, application code can become tightly coupled to one
provider's API, request format, response format, authentication, and
error handling. Spring AI offers a common programming model so
application code can focus on business functionality while
provider-specific integrations are handled by model implementations and
starters.

### 1.2 Why use Spring AI?

-   **Spring Boot integration:** configuration, dependency injection,
    and auto-configuration.
-   **Provider abstraction:** integrate supported model providers
    through familiar APIs.
-   **Developer productivity:** use Java objects, services, and
    configuration instead of manually constructing every provider
    request.
-   **RAG support:** connect documents, embeddings, and vector stores.
-   **Tool calling:** allow models to request execution of
    application-defined functions.
-   **MCP support:** connect to MCP servers or expose tools to MCP
    clients.
-   **Operational integration:** work with Spring testing and
    observability patterns.

Spring AI does not make different models identical. Features, context
limits, tool support, structured-output quality, pricing, and latency
still vary by provider.

### 1.3 High-level architecture

``` text
Client / UI
    |
Spring Boot REST Controller
    |
Application Service
    |
Spring AI ChatClient
    |
ChatModel implementation
    |
LLM Provider (cloud or local)
```

For RAG, the application also retrieves relevant context from a vector
store. For tool calling, the model may request that the application
execute a registered tool and then use the result to formulate its
response.

### 1.4 Spring AI vs. LangChain

  -----------------------------------------------------------------------
  Area                    Spring AI               LangChain
  ----------------------- ----------------------- -----------------------
  Primary ecosystem       Java and Spring         Primarily Python and
                                                  JavaScript/TypeScript
                                                  ecosystems

  Integration style       Spring Boot starters,   Language-specific
                          dependency injection,   libraries and
                          Java APIs               integrations

                          services and enterprise applications in
                          Java applications       supported language
                                                  ecosystems

                          vector stores, tools,   retrieval, tools,
                          advisors, MCP           agents, and chains

                          with Spring Boot        LangChain-supported
                                                  stacks
  -----------------------------------------------------------------------

Choose based on the existing stack, required integrations, team
expertise, and production constraints---not only the framework name.

## 2. Spring AI Setup

### 2.1 Prerequisites

-   Java 21 or another Java version supported by the selected Spring
    Boot release
-   Maven or Gradle
-   A compatible Spring Boot version
-   An API key for a hosted provider, or a local model runtime such as
    Ollama
-   Basic Spring Boot and REST API knowledge

### 2.2 Add dependencies

Use Spring Initializr to create a Spring Boot project, then add the
Spring AI BOM and the starter for your chosen provider. For example, an
OpenAI-backed application commonly uses the Spring AI OpenAI starter.

The exact artifact name and version should be taken from the current
official documentation. Avoid mixing Spring AI versions across
dependencies.

Example Maven structure (replace the version placeholder with a
compatible released version):

``` xml
<dependencyManagement>
    <dependencies>
        <dependency>
            <groupId>org.springframework.ai</groupId>
            <artifactId>spring-ai-bom</artifactId>
            <version>${spring-ai.version}</version>
            <type>pom</type>
            <scope>import</scope>
        </dependency>
    </dependencies>
</dependencyManagement>

<dependencies>
    <dependency>
        <groupId>org.springframework.ai</groupId>
        <artifactId>spring-ai-starter-model-openai</artifactId>
    </dependency>

    <dependency>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-starter-web</artifactId>
    </dependency>
</dependencies>
```

> Check the current Spring AI documentation for the starter naming
> convention used by your chosen release. Do not treat this illustrative
> dependency snippet as a substitute for the version-specific setup
> guide.

### 2.3 Configure credentials

Keep API keys outside source control. An environment variable is
preferable to committing a secret in `application.yml`.

``` yaml
spring:
  application:
    name: spring-ai-handbook
  ai:
    openai:
      api-key: ${OPENAI_API_KEY}
```

Set the environment variable in your shell or secret manager:

``` bash
export OPENAI_API_KEY="your-api-key"
```

Use the provider's documented model configuration to select a model.
Model names and availability can change.

### 2.4 Create a REST endpoint

``` java
@RestController
@RequestMapping("/api/ai")
public class AiController {

    private final ChatClient chatClient;

    public AiController(ChatClient.Builder builder) {
        this.chatClient = builder.build();
    }

    @GetMapping("/ask")
    public String ask(@RequestParam String question) {
        return chatClient.prompt()
                .user(question)
                .call()
                .content();
    }
}
```

This example demonstrates the basic request path. For production, prefer
a request DTO, input validation, clear error mapping, authentication,
rate limits, and a response contract rather than exposing arbitrary
model access without controls.

### 3.1 ChatModel vs. ChatClient

`ChatModel` is the model-facing abstraction. `ChatClient` is a
higher-level, fluent API that makes application code easier to read and
compose.

``` java
String answer = chatClient.prompt()
        .user("Explain dependency injection in one paragraph.")
        .call()
        .content();
```

Use `ChatClient` for most application-level interactions. Use
lower-level model APIs when the use case requires direct control over
model requests or responses.

### 3.2 Model providers

Spring AI supports integrations for multiple hosted and local model
providers. Select a provider based on data requirements, model quality,
latency, cost, availability, and required features. Confirm current
provider support in the official reference.

# Part 2 --- Building AI Applications

## 4. ChatClient and Prompt Engineering

### 4.1 System and user messages

A system message defines the assistant's behavior and constraints. A
user message contains the request or data to process.

``` java
String answer = chatClient.prompt()
        .system("You are a concise Java programming assistant.")
        .user("Explain the difference between an interface and an abstract class.")
        .call()
        .content();
```

Prompts should state the task, relevant context, constraints, and
expected format. A system prompt is not a security boundary: never rely
on it alone to protect secrets or enforce authorization.

### 4.2 Dynamic prompt templates

Use variables to reuse a prompt with different input values.

``` java
String answer = chatClient.prompt()
        .user(userSpec -> userSpec
                .text("Explain {topic} for a {level} backend developer.")
                .param("topic", "dependency injection")
                .param("level", "beginner"))
        .call()
        .content();
```

Check the method signatures against the Spring AI version in use. Keep
untrusted user input separate from trusted instructions, and validate
inputs before including them in prompts.

### 4.3 Practical guidelines

-   Give the model one clear task at a time.
-   Provide only the context it needs.
-   Specify the output structure when downstream code depends on it.
-   Include examples when a format is difficult to describe.
-   Test prompts against realistic and adversarial inputs.
-   Version prompts so behavior changes can be reviewed and rolled back.

## 5. Structured Output and Streaming

### 5.1 Mapping responses to Java objects

For application workflows, returning arbitrary text may be inconvenient.
A typed response makes the API contract clearer.

``` java
public record ProductSummary(
        String name,
        String category,
        String summary
) {}
```

A common Spring AI pattern is to request conversion to a target type:

``` java
ProductSummary result = chatClient.prompt()
        .user("Summarize this product: Lightweight travel backpack, 30L capacity.")
        .call()
        .entity(ProductSummary.class);
```

Structured-output conversion does not guarantee that the values are
correct. Validate the returned object, handle missing or invalid fields,
and do not treat model output as trusted data. For strict integrations,
use provider-supported structured output or schema constraints where
available.

### 5.2 Streaming responses

A normal `.call()` waits for a response. Streaming can deliver partial
output as it becomes available, improving perceived responsiveness.

A typical pattern is:

``` java
Flux<String> tokens = chatClient.prompt()
        .user("Explain how a HashMap works.")
        .stream()
        .content();
```

This requires the relevant reactive dependencies and a compatible
streaming endpoint. A Spring MVC application may use Server-Sent Events
(SSE), while a reactive application can return a `Flux` directly.

Consider client disconnects, timeouts, cancellation, partial responses,
and errors that occur after streaming has begun. Streaming output should
not be treated as a complete validated object until the stream finishes.

## 6. Chat Memory

### 6.1 Why memory is needed

LLM calls are usually stateless: a model does not automatically remember
earlier requests. A conversational application must pass relevant prior
messages or retrieve them from a memory store.

Spring AI provides chat-memory abstractions and advisors that can add
conversation context to model calls.

### 6.2 Conversation flow

``` text
User: My order number is A123.
    |
Application associates request with conversation ID
    |
Relevant conversation history is loaded
    |
ChatClient sends history + new message to the model
    |
Assistant response is returned and conversation is updated
```

A conversation ID should identify the intended conversation, not act as
authorization. Verify that the authenticated user has access to that
conversation before loading its history.

### 6.3 Key considerations

-   Choose the appropriate memory implementation for the application.
-   Persist history when conversations must survive restarts.
-   Limit history to fit the model's context window.
-   Summarize or trim older messages when necessary.
-   Avoid storing secrets or unnecessary personal data.
-   Distinguish conversation memory from a RAG knowledge base.

## 7. Tool Calling

### 7.1 What is tool calling?

Tool calling lets an LLM request a defined operation---such as looking
up an order or calculating a value. The application executes the
operation and supplies the result to the model. The model does not
directly execute arbitrary Java code.

### 7.2 Define a tool

The following illustrates the common `@Tool` pattern. Import the
annotation from the Spring AI version used by your project.

``` java
@Component
public class OrderTools {

    private final OrderService orderService;

    public OrderTools(OrderService orderService) {
        this.orderService = orderService;
    }

    @Tool(description = "Get the current status of an order by order ID")
    public OrderStatus getOrderStatus(String orderId) {
        return orderService.findStatus(orderId);
    }
}
```

Register the tool with the chat request using the API supported by your
Spring AI release. For example, releases that support this fluent
pattern allow tools to be supplied to the prompt:

``` java
String answer = chatClient.prompt()
        .user("Check the status of order A123.")
        .tools(orderTools)
        .call()
        .content();
```

### 7.3 Tool-calling safeguards

-   Validate all tool arguments.
-   Enforce user authorization inside the tool or underlying service.
-   Use allowlisted operations instead of arbitrary method execution.
-   Apply timeouts, rate limits, and audit logging.
-   Require explicit approval for consequential actions.
-   Make retryable operations idempotent where possible.
-   Treat tool results as data, not as instructions that override
    policy.

# Part 3 --- RAG and Vector Databases

## 8. Embeddings and Vector Stores

### 8.1 Embeddings

An embedding model transforms text into a numerical vector that
represents semantic features of the text. Text with related meaning can
have vectors that are close under a chosen similarity measure.

``` text
Text
  |
EmbeddingModel
  |
Vector: [0.12, -0.08, 0.31, ...]
```

Embeddings are useful for semantic search, document retrieval,
recommendations, and grouping related content. Vectors from incompatible
embedding models or dimensions should not be mixed in the same index
without a deliberate migration strategy.

### 8.2 VectorStore

Spring AI's `VectorStore` abstraction provides a common way to add
documents and retrieve similar content.

Illustrative example:

``` java
List<Document> documents = List.of(
        new Document("Spring Boot simplifies Java application setup."),
        new Document("Vector search retrieves semantically similar content.")
);

vectorStore.add(documents);

List<Document> matches = vectorStore.similaritySearch(
        SearchRequest.builder()
                .query("How can I quickly create a Java service?")
                .topK(3)
                .build()
);
```

Exact constructors and builder APIs may differ by version. Check the
selected vector-store integration documentation.

### 8.3 PostgreSQL and PGvector

PGvector adds vector storage and similarity search to PostgreSQL. It can
be a practical choice when the application already operates PostgreSQL
and wants to keep relational data and vector retrieval in a familiar
database platform.

Plan for: - Vector dimensions and distance metric - Appropriate indexes
for expected data size - Metadata filters and tenant isolation -
Backups, migrations, and index maintenance - Retrieval latency and
relevance evaluation

A vector store does not replace application authorization. Filter
results so users only retrieve documents they are permitted to access.

## 9. Document Ingestion and RAG

### 9.1 RAG workflow

Retrieval-Augmented Generation supplies relevant external context to a
model at question time.

``` text
INGESTION
Files -> Read documents -> Split into chunks
      -> Generate embeddings -> Store in VectorStore

QUERY
Question -> Embed/search -> Retrieve relevant chunks
         -> Add context to prompt -> LLM -> Answer
```

### 9.2 Document ingestion

A typical ingestion pipeline contains:

1.  **Load:** read PDF, text, Markdown, or other supported content.
2.  **Normalize:** remove irrelevant formatting and handle extraction
    errors.
3.  **Split:** create chunks suitable for retrieval and the model
    context window.
4.  **Enrich:** attach metadata such as source, document ID, tenant, and
    access scope.
5.  **Embed:** convert chunks into vectors.
6.  **Store:** persist content, vectors, and metadata.
7.  **Maintain:** re-index changed files and remove obsolete versions.

Chunk size and overlap depend on document structure, the embedding
model, and the task. Evaluate retrieval quality rather than selecting
arbitrary values.

### 9.3 Build a RAG answer flow

Spring AI provides advisor and retrieval abstractions to reduce custom
orchestration. Depending on the selected version and design, options
include `QuestionAnswerAdvisor` and the more composable
`RetrievalAugmentationAdvisor`.

A conceptual example:

``` java
String answer = chatClient.prompt()
        .user("What is our leave policy?")
        // Configure the appropriate RAG advisor for your Spring AI version.
        .call()
        .content();
```

The advisor must be configured with the intended vector store and
retrieval settings; the snippet above only illustrates where the user
query enters the chat flow.

### 9.4 RAG quality checklist

-   Retrieve relevant chunks, not merely the most similar chunks.
-   Apply metadata filters and authorization before exposing context.
-   Keep source identifiers so answers can cite documents.
-   Tell the model to acknowledge insufficient evidence.
-   Evaluate retrieval and answer quality separately.
-   Defend against malicious instructions embedded in retrieved
    documents.
-   Do not assume RAG eliminates hallucinations.

# Part 4 --- Agents and MCP

## 10. Building AI Agents

### 10.1 What makes an AI agent?

An agent uses a model to choose and coordinate actions toward a goal. It
may call tools, inspect results, and continue until a stopping condition
is reached.

``` text
User Goal
   |
LLM decides next step
   |
Tool executes an action
   |
Result returned to LLM
   |
Continue or produce final answer
```

A tool-enabled chatbot is not necessarily a fully autonomous agent. The
difference depends on how much control the model has over action
selection and multi-step execution.

### 10.2 Building blocks

-   **LLM:** interprets the task and selects the next action.
-   **Tools:** perform specific operations through controlled
    application APIs.
-   **Memory/context:** preserves relevant information.
-   **Orchestration:** controls sequence, state, retries, and stopping
    conditions.
-   **Guardrails:** enforce permissions, limits, and approval
    requirements.

Start with a bounded workflow before building a highly autonomous agent.
For deterministic business processes, ordinary Java orchestration may be
safer and easier to test than an open-ended agent loop.

### 10.3 Example use case

An order-support assistant could: 1. Validate the user's identity and
request. 2. Call an order lookup tool. 3. Retrieve the relevant delivery
policy. 4. Explain the current status with supporting evidence. 5. Ask
for human approval before initiating a consequential change.

Always limit tool calls and execution time. Use explicit stopping
conditions and ensure that the application---not the model---enforces
permissions.

## 11. Spring AI and MCP

### 11.1 What is MCP?

Model Context Protocol (MCP) is a standard for connecting AI
applications to external tools and context. You have already covered MCP
fundamentals; this chapter focuses on Spring AI integration.

MCP defines three commonly used server capabilities: - **Tools:**
executable operations - **Resources:** data or context exposed by a
server - **Prompts:** reusable prompt templates exposed by a server

### 11.2 MCP architecture

``` text
Spring Boot AI Application
          |
     Spring AI MCP Client
          |
     MCP transport
          |
       MCP Server
          |
  External API / Database / Tool
```

A Spring AI application can act as an MCP client to discover and call
tools from a server. A Spring Boot application can also expose selected
functionality through an MCP server integration.

### 11.3 MCP vs. native Spring AI tools

  -----------------------------------------------------------------------
  Spring AI tool calling              MCP
  ----------------------------------- -----------------------------------
  Tools are registered with the       Tools are exposed through an MCP
  application/model interaction       server

  Useful for local Java methods and   Useful for reusable tools shared
  Spring services                     across clients

  Application manages tool            MCP defines a protocol for
  registration and execution          discovery and communication

  Usually tightly integrated with     Can separate tool implementation
  application code                    from the AI host
  -----------------------------------------------------------------------

MCP does not replace Spring AI's model APIs. It complements them by
standardizing access to external capabilities.

### 11.4 Integration checklist

-   Choose a supported transport, such as STDIO or HTTP-based transport,
    according to the server and Spring AI release.
-   Configure the MCP client and server dependencies.
-   Discover and inspect available tools.
-   Allowlist tools relevant to the application.
-   Secure transport and credentials.
-   Validate tool arguments and results.
-   Set timeouts and audit sensitive operations.

Consult the official Spring AI MCP documentation for release-specific
configuration and code examples.

# Part 5 --- Production-Ready Spring AI

## 12. Advisors and Advanced Capabilities

### 12.1 Advisors API

Advisors provide reusable behavior around chat interactions. Depending
on the implementation, an advisor can inspect or augment requests and
responses, add context, or apply cross-cutting logic.

Typical applications include: - Chat memory - RAG and retrieval -
Request/response logging - Custom prompt enrichment - Reusable policy
checks

Use advisors to organize common behavior, but do not put critical
authorization only in an advisor. Enforce security in the application
service and data-access layer as well.

### 12.2 Multimodal AI

Multimodal models can work with combinations of text, images, audio, and
other supported inputs or outputs. Capabilities depend on the selected
model and Spring AI integration.

Examples: - Extracting information from an invoice image - Summarizing a
supported audio recording - Answering questions about a product image -
Generating text or images where the provider supports it

Confirm supported media types, size limits, model options, and pricing
before implementing a workflow.

### 12.3 Model selection

Compare models using a representative evaluation set. Consider: - Answer
quality and reliability - Tool-calling and structured-output support -
Context window - Latency and throughput - Input/output token cost - Data
residency and privacy - Availability and operational limits

A model that performs well on a demo may not be the best model for a
production workload.

## 13. Testing, Observability and Security

### 13.1 Testing

LLM outputs can vary, so combine ordinary software tests with
AI-specific evaluation.

-   **Unit tests:** validate business logic without calling a real
    model.
-   **Integration tests:** verify provider, vector-store, and tool
    wiring.
-   **Contract tests:** validate required response fields and tool
    arguments.
-   **RAG tests:** check retrieval relevance, permissions, and source
    attribution.
-   **Evaluation tests:** assess answer correctness, relevance, and
    groundedness on a fixed dataset.
-   **Regression tests:** compare quality after prompt, model, or
    retrieval changes.

Use deterministic test doubles for most unit tests. Reserve
real-provider tests for controlled integration or evaluation suites.

### 13.2 Observability

Track enough information to troubleshoot failures without leaking
sensitive data.

Useful signals include: - Request latency and error rates -
Model/provider and model version - Token usage and estimated cost -
Tool-call count, duration, and failures - Retrieval latency and result
counts - Timeout and retry metrics - Trace IDs linking the application
request to AI operations

Spring AI integrates with Spring observability and Micrometer
facilities. Confirm which operations are instrumented in the selected
release. Treat prompts, model responses, and retrieved documents as
potentially sensitive; avoid logging their full contents by default.

### 13.3 Security essentials

-   Store provider credentials in a secret manager or
    environment-specific secret store.
-   Authenticate users and authorize each business operation.
-   Defend against prompt injection in user input and retrieved content.
-   Treat model output and tool arguments as untrusted input.
-   Validate and constrain tool execution.
-   Apply request-size limits, rate limits, and usage budgets.
-   Avoid sending unnecessary personal or confidential data to external
    providers.
-   Define retention, redaction, and audit policies.
-   Require approval for sensitive or irreversible actions.

## 14. Deployment and Best Practices

### 14.1 Deployment architecture

``` text
Client
  |
API Gateway / Ingress
  |
Spring Boot Application
  |             |
LLM Provider    Vector Store
  |
Metrics / Logs / Traces
```

Deploy the Spring Boot service like other production services, while
also accounting for external model-provider availability, rate limits,
and usage cost.

### 14.2 Production checklist

**Configuration** - Separate development, test, and production
settings. - Keep API keys out of source control and container images. -
Configure model names and provider endpoints externally.

**Reliability** - Set connection and response timeouts. - Retry only
appropriate failures and use bounded backoff. - Add concurrency controls
and circuit breakers where appropriate. - Provide a clear error response
when the model is unavailable.

**Performance and cost** - Track token usage and latency per feature. -
Limit prompt size and retrieved context. - Cache only when the use case
permits it and data isolation is preserved. - Avoid unnecessary repeated
model calls. - Set per-user and per-application usage budgets.

**Security** - Authenticate endpoints and authorize data access. - Apply
tenant-aware filters to RAG queries. - Audit tool calls that affect
business data. - Redact secrets and sensitive values from logs.

**Operations** - Add health checks and monitoring. - Test provider
failures and deployment rollbacks. - Version prompts and evaluate model
changes before rollout. - Document operational limits and escalation
paths.

Docker and Kubernetes can be used for deployment, but the application
still needs sound timeout, scaling, security, and observability
configuration.

## Final advice

Learn Spring AI by building small, testable features rather than
starting with a fully autonomous agent. Begin with a chat endpoint, add
structured output and tools, then implement RAG, memory, and MCP. Before
production, focus on access control, evaluation, observability,
reliability, and cost.

The goal is not just to make an LLM respond. It is to build a Spring
Boot application in which AI behavior is useful, testable, secure, and
operationally manageable.
